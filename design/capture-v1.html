Stay awake, so the add is an event.

iOS never wakes a suspended app for a contact change. The only way an add can be an event on this phone is for the process to already be running when it happens. So v1 keeps TouchedTips resident with a low-power location session, and treats every other wake source as the net that catches it when iOS kills the process. One idempotent tick sits under everything. Nothing leaves the phone. Setup is three permission prompts and nothing else.

Five layers

Read top to bottom as "what makes it fast", "what makes it survive", "what does the work".

1Presence
Keeps the process alive so the contact-change notification arrives live. Legacy location manager: background updates allowed, automatic pausing off, three-kilometre accuracy, no distance filter. GPS stays off; fixes come from cell and Wi-Fi. Started on every launch once Always is granted. A PresencePolicy gates it: Always by default, At places or Off from Settings if the battery numbers say so.
CLLocationManager allowsBackgroundLocationUpdates pausesLocationUpdatesAutomatically = false desiredAccuracy = 3 km showsBackgroundLocationIndicator = false
2Relaunch net
Brings the process back after iOS kills it, and narrows the add window while it is dead. Visits stay. Add significant-change monitoring, one breadcrumb geofence re-dropped at the current coordinate on every wake, and a background refresh floor. Location events relaunch even after a force-quit.

3Event
The add itself, when Presence is holding. Coalesce for 300 ms, since one save emits several notifications, then tick. The current one-second debounce goes.
CNContactStoreDidChange
4Tick
One function, every path. Diff, witness fix, resolve, name, notify, heartbeat, re-drop fence. Idempotent through the change-history token. Runs inside a background task so a relaunch gets its thirty seconds.
CaptureCoordinator.tick(source:)
5Core
Unchanged shape. Person, Place, Visit, Meet, KV. Two additions: a heartbeat table (source, at, battery level) and a new VisitSource.fix for zero-length witness fixes, so the resolver sees a fix as a visit that contained the add.
GRDB · TouchedTipsCore Resolver stays pure
Why the legacy API. The iOS 17 live-updates API pauses when the device is stationary and lets the app suspend, which is exactly the moment you are standing in a café meeting someone. The older manager with automatic pausing disabled is the one that holds. Whether it still holds on iOS 26 is the first spike.

The tick, in order

tick(source):
  heartbeat(source, now, batteryLevel)                      -- every wake is measured
  changes = ContactsDiff(since: token)
  if changes.added.isEmpty: rearmFence(); return

  fix = await requestLocation(best, timeout 8 s)            -- precise, one shot, only when there is an add
  if fix: Visit(source: .fix, start = end = now, place = Place.findOrCreate(fix))

  for add in changes.added:
    window = [lastHeartbeat, now]                            -- seconds when Presence held, minutes to hours when it did not
    meet   = Resolver.meet(add, visits overlapping window ± 2 h)
             -- .fix visit inside the window wins → .witnessed
             -- else visit containing the window → .witnessed
             -- else nearest visit within 2 h     → .inferred    (the breadcrumb fence is one of these)
             -- else                              → .dateOnly
    name   = nearbyPOI(meet.place) ?? reverseGeocode(meet.place)
    notify(add, meet, name)

  save token; rearmFence()

The resolver's only new rule is that a fix visit outranks an ongoing long visit. Without it, a zero-length overlap ties with a café you have sat in for an hour, and the tie-break is arbitrary.

No Shortcuts, no server, no account. An optional CheckForNewPeople App Intent is exposed for people who want a Shortcuts automation on Contacts or Messages closing, and an I just met someone intent for the Action Button records a fix on demand. Both are accelerators behind a settings row, never required.

Failure modes

What happensWhat the user sees
iOS kills the resident process for memoryThe next fence exit, significant change or visit relaunches it. The add is caught then, with the fence you were inside as the place, at inferred tier. Presence re-arms on launch.
User force-quits the appSame as above. Location events relaunch after a force-quit; the notification arrives on departure instead of on the spot.
Contact added with the phone in a pocket, far from any placeFix comes back with a coordinate and no POI. Body says the street, tier witnessed.
Contact synced in from iCloud while stationary at homePresence catches it live. Fix says home. The user taps Not a meeting or Fix place.
Always downgraded to While Using in SettingsPresence stops; the app becomes v0 with a banner in Settings.
Change history resetDrop-everything event. Ingest only inserts unseen people, as today.

What the heartbeat table answers

  • Uptime fraction. Share of five-minute slots in the last day with a heartbeat. This is how often Presence actually held. Target unmeasured until the spike.
  • Battery per day with Presence on versus off, from battery level sampled at each heartbeat. Rough, on-device, and enough to choose between the always and duringVisits policies.
  • Wakes by source and the add window width at each meet. Shows whether the relaunch net is doing anything once Presence is on.
  • Add to notification latency, from the fix timestamp to the notification post.

The Dev section of Settings shows these numbers. They decide the policy default; the doc does not.
