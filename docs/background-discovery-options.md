# Background contact discovery options

Research date: 2026-09-09. This document separates documented API behavior from proposed TouchTips experiments. No option below has been installed or validated on the phone as part of this research.

## What suspension means

iOS normally suspends an app after it leaves the foreground: its process may remain in memory but receives no execution time. Background capabilities provide execution for particular features; an entry in the app switcher does not confer execution. This reduces battery use and system load. [Apple DTS explanation](https://developer.apple.com/forums/thread/841001)

Contacts offers `CNContactStoreDidChange` and a persisted change-history cursor. Neither documented interface provides a contact-save background launch contract. Searches of current Apple Contacts and NameDrop documentation found no public NameDrop completion or external contact-save wake API. This is a conclusion from the documented API surface, not a claim about private system internals. History fetch preserves discovery after the app next executes. [Contacts notification](https://developer.apple.com/documentation/foundation/nsnotification/name-swift.struct/cncontactstoredidchange), [Contacts history](https://developer.apple.com/documentation/technotes/tn3149-fetching-change-history-events)

Apple DTS also answers an almost identical request to poll Contacts from a periodic timer: iOS provides no such general-purpose background timer. [Contacts timer question](https://developer.apple.com/forums/thread/765729)

## Repair the existing location fallback

The companion source/SDK review found TouchTips consumes `CLMonitor.events` without retaining a `CLServiceSession` requiring `.always`. Modern Core Location sessions express a feature's continuing authorization requirements; sessions should span that feature, and be recreated promptly when the system relaunches the app for delivery. Holding the appropriate session can let Core Location resume or relaunch an app when new authorized information is available. This is a concrete repair to investigate in the geofence fallback. It does not establish that the separate legacy `CLLocationManager` path suspended because this object was missing. [WWDC24: location authorization](https://developer.apple.com/videos/play/wwdc2024/10212/), [background location configuration](https://developer.apple.com/documentation/corelocation/handling-location-updates-in-the-background)

The phone's 3 km accuracy request should not be declared invalid solely because it is coarse. Apple explicitly suggests `pausesLocationUpdatesAutomatically = false` plus `kCLLocationAccuracyThreeKilometers` for power-friendly background updates. Apple DTS recommends the lowest accuracy that meets the actual location feature's needs, without promising that a particular setting gives continuous execution. The internal `cblsPowerSaver` / intermediation log labels have no public contract found in this research. Changing accuracy is an experiment, not an established cure. [Automatic-pause documentation](https://developer.apple.com/documentation/corelocation/cllocationmanager/pauseslocationupdatesautomatically), [Apple DTS discussion](https://developer.apple.com/forums/thread/841001)

## A real active session can help, with limits

`CLBackgroundActivitySession` plus `CLLocationUpdate.liveUpdates()` is a supported path for location work continuing in the background. Retain the activity session; start a new one in the foreground and recreate it promptly if rejoining after a background relaunch. Apple describes the visible location indicator as keeping When In Use access active. A Live Activity can also support an ongoing location session. [WWDC23: streamlined location updates](https://developer.apple.com/videos/play/wwdc2023/10180/)

This is not a permanent keep-alive contract. Apple explicitly says Core Location does not keep an app continuously running when it has nothing to deliver. `liveUpdates` can suspend when stationary or when no location fix is available, then resume or relaunch when updates return. Consequently, even a modern location session does not document immediate detection of a contact created while the user sits still. [WWDC24](https://developer.apple.com/videos/play/wwdc2024/10212/), [WWDC23](https://developer.apple.com/videos/play/wwdc2023/10180/)

A user-started meeting/event session that actually records location could be tested. Its cost is location visibility and additional battery use; the energy cost must be measured. Keeping location active solely to bypass suspension does not match Apple's requirement that background categories follow the feature provided to the user. [Location energy guidance](https://developer.apple.com/documentation/xcode/accessing-the-device-s-location-efficiently), [Apple DTS guidance](https://developer.apple.com/forums/thread/841001)

There is another session experiment on iOS 26+: `BGContinuedProcessingTask`. Its documented purpose is continuing user-initiated work, with visible progress and cancellation. In August 2026, Apple DTS explicitly endorsed a broader user-started performance session for a MIDI app waiting on events, while acknowledging the progress-model mismatch. DTS says there is no fixed maximum runtime, but contention can end the task. This is stronger evidence than saying all session approaches are impossible, but it is guidance for another use case, not a guarantee or specific endorsement for TouchTips. An event session would need honest progress/status, cancellation and interruption handling; it would not become an invisible, indefinitely active Contacts observer. [Task request](https://developer.apple.com/documentation/backgroundtasks/bgcontinuedprocessingtaskrequest), [Apple DTS session discussion](https://developer.apple.com/forums/thread/840384)

## Explicit actions without opening the full app

| Option | What it can do | What it does not do |
| --- | --- | --- |
| App Intent behind a Control Center, Lock Screen or widget button | Run a short capture/check action following one interaction. App Intents support background execution; widget interactions invoke `perform()`. | Automatically observe an unrelated Contacts save. Permissions, execution target, shared storage and locked-device behavior need implementation and phone testing. |
| Share Contact → TouchTips | An extension can receive the contact deliberately shared from Apple Contacts and persist the capture without requiring the full app UI. | Automatically intercept Save or NameDrop. Adds explicit sharing steps. |
| Personal Shortcuts automation | User configures “Contacts is closed” → TouchTips capture intent, allowing a scan when switching away from Apple Contacts. App automations can run without asking each time. | Trigger on the save itself, cover NameDrop automatically, or silently configure the user's automation during app installation. |

Sources: [App Intent execution](https://developer.apple.com/documentation/appintents/creating-your-first-app-intent), [widget actions](https://developer.apple.com/documentation/widgetkit/adding-interactivity-to-widgets-and-live-activities), [Controls](https://developer.apple.com/documentation/appintents/widgets-live-activities-and-controls), [Contacts sharing](https://support.apple.com/guide/iphone/iph3e0ca2db/ios), [vCard type](https://developer.apple.com/documentation/uniformtypeidentifiers/uttype-swift.struct/vcard), [extension shared containers](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/ExtensionScenarios.html), [Shortcuts app triggers](https://support.apple.com/guide/shortcuts/apde31e9638b/ios), [automatic execution](https://support.apple.com/guide/shortcuts/apd602971e63/ios), [user-created automation](https://support.apple.com/guide/shortcuts/apdfbdbd7123/ios).

These are supported building blocks, not implemented TouchTips capabilities. A widget extension cannot assume access to the app's private SQLite container; an extension architecture must share storage safely. For a share extension, receiving a vCard also does not itself prove the corresponding existing Contacts identifier, so avoid creating duplicate system contacts. [Extension isolation](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/ExtensionScenarios.html)

## Why a server is not the direct fix

Remote notifications are useful when the server knows an event occurred. Inference: a server cannot learn that a purely local contact was saved without another data feed telling it. Periodic silent pushes merely add another opportunistic wake source: Apple does not guarantee delivery, may delay them, and recommends attempting no more than two or three per hour. This cannot promise seconds-level discovery. [Background push delivery](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app)

## Practical recommendation

The desired product remains automatic, local and low power after initial permission setup. Repair the modern location authorization session and its launch/recovery lifecycle, coalesce scans on every supported wake, and preserve the durable Contacts history/outbox path. Shortcuts and recurring manual Start actions do not meet that requirement and are not the proposed implementation. The explicit-action options above remain an account of the alternatives researched, not the primary recommendation. An untouched Apple Contacts/NameDrop workflow with immediate all-day notifications has no documented guarantee in the APIs examined here.

## Device evidence

On September 9, the Testy contact was saved in Apple Contacts at 11:52:31.866 EDT. RunningBoard had suspended the TouchTips process at 11:52:09.990. The same process resumed into the foreground at 11:53:24.065 and submitted the notification at 11:53:24.504. Before reopening, the copied database contained neither Testy nor a pending notice; after reopening it contained Testy with no pending notice. Focus allowed the submitted notification. Private source logs remain under the main checkout's ignored `build/phone-audit-20260909-testy/` directory.

Source review also confirms `UIBackgroundModes` already includes location and fetch, Always permission was granted, and the legacy manager requested background updates with automatic pausing disabled. These facts rule out a simple missing location-capability checkbox. Internal power-saving log messages do not prove that changing requested accuracy would prevent suspension.

## Implementation in this PR

`CaptureFence` owns the explicit `.always` session and one persisted `TouchedTipsFence` monitor. Launch restores the session synchronously; monitor creation waits for protected data. Subsequent launch/foreground, location, refresh and protected-data callbacks can retry an ended event stream. Authorization loss cancels observation and releases the session. [Monitor persistence and protected data](https://developer.apple.com/documentation/corelocation/clmonitor-6ynwz/requestmonitorwithconfiguration:completion:)

The existing 150 m fence survives nearby fixes and replaces its condition using the same identifier without a remove/add gap. Writes are serialized, the latest location received while opening wins, and reset waits for an in-flight write before removing the fence. Fresh fixes (within two minutes, accuracy at most 150 m) can reanchor after a 75 m movement. These thresholds are implementation choices, not Apple delivery guarantees. If only coarse fixes are available, the old fence remains; a new installation waits for a sufficiently accurate fix before creating one. The app does not increase requested location accuracy to obtain that fix. [Replacing a monitored condition](https://developer.apple.com/videos/play/wwdc2023/10147/)

The dev panel labels sampled execution coverage, whole-device battery change, and detection-to-submission latency explicitly. None measures the delay between a contact save and the first opportunity to run. The existing Contacts history cursor, durable notification outbox, visit/significant-change tracking and coarse standard updates remain in use.

Regression tests exercise authorization, owner release, protected-data availability, interrupted setup, event-stream recovery, persisted conditions, stale/coarse fixes, and reset/write races using an injected monitor. They do not simulate iOS suspension or prove physical geofence delivery. Before claiming a user-visible improvement, repeat the Testy scenario on a stationary phone with Instagram foregrounded, then test movement, locking, NameDrop, offline use, relaunch and permission changes separately. Compare save, observer, submission and visible-alert timestamps. Measure battery over longer sessions independently.

## Follow-up: automatic operation and overlooked APIs

The deeper review checked the current Contacts/ContactProvider interfaces, modern Core Location authorization and delivery, continued processing, interprocess notifications and contact-account synchronization. No public contact-save or NameDrop launch hook was found. This remains a finding about the documented interfaces examined, not a proof that iOS will never gain one.

| Candidate | Documented behavior | Consequence for automatic TouchTips capture |
| --- | --- | --- |
| Contact Provider extension | Publishes contacts managed by the app to the system; the app signals new data, and the system also schedules low-priority overnight synchronization on power. | Its direction is app → Contacts. It is not a callback when another account or Apple Contacts saves a contact. [ContactProvider](https://developer.apple.com/documentation/contactprovider) |
| Darwin/dispatch notification observer | Apple DTS states Darwin notifications do not resume or relaunch a suspended or terminated process. `deliverImmediately` is ignored for Darwin notification centers. | Replacing `CNContactStoreDidChange` with a lower-level observer does not obtain background execution; undocumented notification names are not supported APIs. [DTS explanation](https://developer.apple.com/forums/thread/69333), [CF notification behavior](https://developer.apple.com/documentation/corefoundation/cfnotificationcenterpostnotification(_:_:_:_:_:)) |
| `CLServiceSession(.always)` | Expresses continued authorization interest for modern monitoring; restore outstanding session state promptly after process launch. | Repair the actual missing lifecycle dependency. It authorizes later location-event delivery, not arbitrary CPU time or a Contacts-save trigger. [Location authorization](https://developer.apple.com/videos/play/wwdc2024/10212/) |
| Continuous modern location updates | Support background delivery, but stationary/no-fix periods can suspend execution. Higher-accuracy location consumes more energy. | Do not raise accuracy or run GPS continuously solely to keep Contacts scanning. No source establishes that modern sessions simultaneously guarantee stationary prompt discovery and low all-day battery use. [Location energy guidance](https://developer.apple.com/documentation/xcode/accessing-the-device-s-location-efficiently), [delivery lifecycle](https://developer.apple.com/videos/play/wwdc2023/10180/) |
| Continued processing after onboarding opt-in | The task must start from the foreground in response to a person's action, show progress and allow cancellation. | No source found establishes that a one-time onboarding opt-in authorizes invisible automatic session renewal indefinitely. The MIDI-session analogy is insufficient to infer that. [Task requirements](https://developer.apple.com/documentation/backgroundtasks/performing-long-running-tasks-on-ios-and-ipados/) |

### Best supportable automatic architecture

Use location for the existing location-history feature and reuse its execution opportunities for a short, coalesced Contacts-history fetch. Visits are Apple's most power-efficient location service and arrive after the visit; significant-change tracking is a low-power cellular/Wi-Fi service; standard location is more regular but costs more power. A significant-change event can relaunch the app, provided the service is restored on launch. These are useful autonomous wake sources, but their triggers follow movement or visits, not contact creation. [Choosing location services](https://developer.apple.com/documentation/corelocation/getting-the-current-location-of-a-device), [significant-change relaunch](https://developer.apple.com/documentation/corelocation/cllocationmanager/startmonitoringsignificantlocationchanges())

The implementation should retain the explicit authorization session while the already-enabled presence feature needs it, recreate monitoring promptly, release it when that feature stops, and log session diagnostics and wake causes. Reconcile once per actual wake opportunity, commit the Contacts cursor and outbox durably, submit promptly, and avoid repeated full scans or high-frequency polling. This is an architectural recommendation based on the documented lifecycle above; battery and delivery gains require physical-device measurement.

### What contact-account push would change

A server can detect a contact change only if it has access to the account receiving that change. CloudKit exposes containers belonging to the app, not a general subscription to the device's iCloud Contacts database. [CloudKit container boundaries](https://developer.apple.com/documentation/cloudkit/ckcontainer)

Account-specific integrations can move event detection to a server:

| Account | Supportable event source | Limits |
| --- | --- | --- |
| User-owned CardDAV server | Apple Contacts supports CardDAV accounts and lets the user select a default account for new contacts. CardDAV creates new server records with `PUT`; an owned server can add a durable event/outbox when it accepts a create. | Requires account and default-account setup plus server/APNs implementation. It observes only records uploaded to that account; NameDrop routing needs device validation. [Apple account setup](https://support.apple.com/guide/iphone/iph7edacccf9/ios), [CardDAV creation protocol](https://www.rfc-editor.org/rfc/rfc6352.html#section-6.3.2) |
| Microsoft/Outlook account | Microsoft Graph provides creation/update/deletion webhooks for contacts with `Contacts.Read` authorization. | Covers the subscribed account, requires subscription renewal and recovery, and still waits for device-to-account synchronization. [Microsoft contact subscriptions](https://learn.microsoft.com/en-us/graph/outlook-change-notifications-overview) |
| Google account | People API supports authenticated incremental contact synchronization. | The reviewed API is polling, not a documented contact webhook, and Google explicitly allows several minutes of write propagation for sync requests. [Google incremental sync](https://developers.google.com/people/api/rest/v1/people.connections/list) |

The CardDAV proposal is an inference from supported protocols: `Apple Contacts save → upload to owned account → durable server event → alert APNs`. iOS can present an alert notification while TouchTips is not running, so this removes TouchTips execution as the detection prerequisite. It does not guarantee that a local save uploads immediately, nor that APNs/Focus presents the alert immediately. [System notification presentation](https://developer.apple.com/library/archive/documentation/NetworkingInternet/Conceptual/RemoteNotificationsPG/SchedulingandHandlingLocalNotifications.html)

This could preserve normal Apple Contacts use after one-time account setup and keep contact hosting under the user's control. It is nevertheless a separate backend/account architecture: contacts in other accounts remain outside its event source, changing the default account is not a migration of existing records, and offline saves must wait for synchronization. No arbitrary iCloud Contacts webhook was found. A viable implementation would also reconcile server identifiers with local Contacts identifiers and deduplicate server/local alerts. None of this backend or account setup belongs in the current location-lifecycle repair PR.

With the current local-first requirement, the defensible PR improves automatic wake recovery and minimizes avoidable work. It must not claim that the stationary Testy failure is fixed until a device test demonstrates that path, or that a handful of successful tests establishes always-on delivery.
